以前の「グラフ簡約(call by need) + 正格性解析」では、副作用の扱いが簡約器の実装に強く依存するなど、 汎用言語として大きな弱点を抱えていました。 このため、現在進行中のrevappコンパイラの作成では既に、入出力関数に「世界型」を導入しています。

GPLv3も十分強力なコピーレフトライセンスです。しかしGPLv2を使用していた多くのプロジェクトなどに引きずられ、コピーレフトの 追求が中途半端になりました。AGPLv3(GNU Affero General Public License version 3)は、GPLv3で実現出来なかったコピーレフトの追求を極めた、現時点で最強のコピーレフトライセンスです。開発者がまだ私しかいない当 ソフトにとって、ライセンスの切り替えによるデメリットは殆どなく、中途半端なライセンスを使うメリットはありません。

2013年12月12日…コンパイラのアップデート

従来の実装では、括弧を単位としてラムダ計算をコンビネータに置き換えていました。しかしこの方法だと副作用を扱うときに、右結合に統一し たにも拘らず余分に括弧を使わねばならない場合があります。
例えば、以下のコード
(=self =done (done getc)=c (((= ()) c) self)=next =cont next c cont)
の「(((= ()) c) self)=next」の部分は、直後の「=cont」に引数が与えられるまでクロージャ生成(実行予約)が行われません。なぜなら、一組の括弧では一つ のコンビネータしか作らないため、=self,=done,=contの三つの仮引数を一つのコンビネータが引き受けるからです。=cont まで引数が与えられないとコンビネータは動作せず、(((= ()) c) self)の実行予約もメモ化も行われません。従来のコンパイラでこれを防ぐには、
(=self =done (done getc)=c (((= ()) c) self)=next (=cont next c cont))

の様に=contの手前で括弧を追記する必要がありました。
新しいコンパイラでは、クロージャを生成する括弧を複数のコンビネータに分割することで、右結合による括弧の省略の有無で動作が変わらないよ うにしました。

Executive summary - 要約

revappは、関数引数のメモ化と遅延評価を評価戦略とする、ラムダ計算に基づいた関数型プログラミング言語で す。

類似の他のプログラミング言語との違いは、それらのプログラミング言語が持っているほとんど全ての機能が、revappには欠けていること です。例えば、統合されたHindley-Milner多相型システムの提供等です。また、標準では組み込み関数が一切用意されておらず、外 部ライブラリの助け無しには計算機の電力消費を増加させることしか出来ません。それにも拘らず、revappはチューリング完全なのです。

syntax - 文法

revappの文法をBNF記法で表すと以下の様になります。
<expr> ::= "="<identifier> | <identifier> | <expr> <expr>
ただし、<identifier>は文字数が0以上の文字列とします。

結合順位を明示するために括弧を使うことが出来ます。カッコがない場合、全ての構文は右結合優先の原則に従います。例えば"a (=b c)"では、"=b c"を囲むカッコが不要で"a =b c"と書いても同じ意味になります。括弧まで含めた文法は
1. <term> ::= <identifier> | "="<identifier> | "(" <expr> <expr> ")"
2. <expr> ::= "(" <expr> ")" <expr> | <term>
となります。

(=x x x)=x x x

何故revappが必要とされるのか

或いは、「ラムダ式」の何処が間違っていたのかについて。

ラムダ式の表現する計算体系・ラムダ計算は、チューリング完全な最小の計算体系です。一つの変換規則と一つの関数定義規則しか持たず、組み 込み関数に至っては全く存在しません。よってラムダ計算を素直に表現すれば、チューリング完全な最小のプログラミング言語が生まれるはずでし た。しかし代わりに、ラムダ計算の生みの親であるアロンゾ・チャーチとスティーヴン・コール・クリーネは、それ以前の数学体系の表記法を使っ てラムダ計算を表現しました。こうして生まれたのが「ラムダ式」です。

二つの引数x,yを取る関数f(x,y)=x+yを考えてみましょう。チャーチ達が作ったラムダ式では、先の式の左辺に現れた変数の順番を 踏襲して「f=λxy.x+y」と表現します。また、関数適用の順番も、数学の表記に近い「f 3 2 = f(3,2)」となるように左結合に定め、「f 3 2」と「(f 3) 2」は同じ式になるように表現します。ということは、 「(λxy.x+y) 3」の様に、引数を二つ取るfに一つずつ値を適用する場合、λ記号の直後の変数から代入が行われる事になります。従っ て、「λxy.x+y」は「λx.(λy.x+y)」と同値となり、変数への代入は右結合となります。結果、関数適用とラムダ抽象では結合の 順番が逆になっています。また、「λx.g x 3」と「(λx.g x) 3」の様に、ラムダ抽象に束縛されている変数と、ラムダ抽象の外 側の引数を区別するため、括弧を多用しなければなりません。そして何より、「f=λxy.x+y」の様に、関数fを定義するのに等号「=」が 必要となります。

この様に冗長な表記法をチャーチ達が選ばざるを得なかったのは、生みの親の宿命です。ラムダ計算発見当初は、チャーチ達以外の人々はラムダ 計算を知らないからです。ラムダ計算の素直な表現は、ラムダ計算を知らない人に取っては暗号文に過ぎません。しかし、チャーチ達の偉大な発見 が常識となった今、当時の冗長な表記法に拘る必要はありません。

revappでは関数適用の順番を逆にして、関数適用もラムダ抽象も右結合で統一しています。嬉しいことに副作用として、「3 λx g x」の様にラムダ抽象の束縛部分と引数部分がλ記号で分断され、括弧の使用を節約できます。また、変数を示すラムダ記号と、その変数に適用さ れる引数を隣接させる事ができ、ラムダ記号を等号「=」の様に用いることが出来ます。revappでは、ラムダ記号ではなく等号でラムダ抽象 を表現します。

今後の予定…入出力・副作用

純粋なラムダ計算には「参照透過性」という性質があります。 計算の表現と、その計算を実行した結果である返り値は等価であり、言語処理系の都合で交換可能であるということです。 この性質により、より効率の良い計算方法を言語処理系は選択出来ます。 しかし古典的な「計算」には、入出力などの副作用の視点が欠けています。 返り値の予測を言語処理系が行えば、「与えられた文字一文字を画面に印字する」など出力関数は省略されてしまうかも知れません。 入力関数は何度も呼び出されてしまうかも知れません。 計算の順番も言語処理系の都合で入れ替わったりするでしょう。

revappでは副作用を扱うため、三つの仕組みを用いる予定です。

一つ目は、既に導入済みの、関数引数のメモ化です。メモ化は関数引数に束縛された計算の評価回数を最大一回に制限します。 裏を返せば、関数引数に束縛されていない計算については参照透過性を緩め、メモ化の範囲を処理系の都合で変えられるということです。 本来、参照透過性が完全に実現された処理系であれば、メモ化は関数引数以外の全ての計算に適用され、副作用の実行回数は最小となります。 しかしそのためには、任意の計算の同一性を判定するという、ゲーデルの不可能性定理への反例を実装せねばなりません。 とはいえ、実行回数は処理系の効率を左右する重要な要素の一つであり、最小は不可能でも、処理系の解析能力が許す限り、減らすことは重要で す。 逆に言えば、ブートストラップ用インタプリタや組み込みマイコンなどの貧弱な処理系では、同一計算の実行回数は増えざるを得ません。 もし、強力な解析能力を持つ処理系に合わせて副作用の実行回数を定めれば、貧弱な処理系しか動かない環境ではrevappは使えなくなりま す。 同様に、貧弱な処理系に合わせて実行回数を定めるのも、処理系の実行効率を落としてしまいます。 副作用の実行回数に幅を持たせることで、revappはこの問題に対処します。 関数引数のメモ化は計算の同一性判定を全く使わないので、貧弱な処理系でも実装できます。 逆に、文法の単純なrevappでは、計算内容に触れずに同一性判定出来る箇所は関数引数だけです。 よって、これでの実行回数をrevappは上限として定めます。 実行回数の下限については勿論、完全な参照透過性でのものです。

二つ目は、プログラムの実行にどの引数の計算が必要かを調べる、正格性解析です。 必要な計算だけ行う点では、既に導入済みの遅延評価も代わり有りません。 しかしラムダ計算で遅延評価を行うと、最も外側の関数部分に一ヶ所しか計算可能な関数がなく、複数の計算を同時に行うことが出来ません。 正確性解析は、関数本体の計算を待たずに計算しても無駄にならない引数を見つけ、並列計算の表現を可能にします。

三つめは、データ構造「世界型」の導入です。 計算機の外側に広がる「世界」というデータ構造を扱う関数として、副作用を解釈します。 勿論、計算機内のデータと違って、入出力関数を実行しない限り、世界の状態を全く言語処理系は知ることができません。 裏を返せば、入出力関数を実行しない限りは、世界の状態を言語処理系がどのように解釈しても、問題は顕在化しません。 revappでは、入出力関数が実行されない限り「世界」は凍ったまま変化せず、入出力関数の実行の前後でのみ変化すると解釈します。 また、入出力関数実行前の「世界」と後の「世界」など、二つの世界が同一か異なるか判定する事も、 宇宙の果てまで観測できない計算機には不可能です。 比較演算が実装不能ということは、裏を返せば比較演算を実装する必要がないということです。 このため、C言語でのvoid型やhaskellやocamlなどでのunit型と同様に、 「世界型」には全くメモリを割り振る必要がありません。 ただし、入出力の結果、二つの「世界」が同一となる場合があるとの解釈を言語処理系に許すのは危険です。 前後の世界が一致する入出力関数を一つでも言語処理系が見つけてしまえば、 その入出力関数の実行回数・タイミングは、副作用のない関数と同様に言語処理系の都合でいくらでも変わってしまいます。 返り値である「世界」の等しい入出力関数が二つあれば、片方の実行だけが行われ、もう一方の実行は省略されるかも知れません。 一旦「世界」が変化するなら、それまで生成されたどの時点の「世界」とも異なるものに変わると、revappでは解釈します。 このように「世界型」というデータ構造を導入すると、 計算機内のデータを引数・返り値として受け渡すことで計算処理の間の依存関係が表現されるのと同じ方法で、 「世界」を引数・返り値として受け渡すことで入出力関数の前後関係が表現出来ます。

例えば、出力関数の多くは、「出力前の世界」と出力値を引数に取り、「出力後の世界」を返します。
=world (world b putc) c putc
このコードでは、bが出力された後にcが出力されます。
=world (world b putc) (world c putc) merge-world
(world b putc)と(world c putc)の間に依存関係が表現されていないため、この二つの処理は並列実行されます。
=world (world c putc) (world c putc) merge-world
二つの(world c putc)は、同一の関数にそれぞれ同一の引数を与えた、同一の計算です。 ならば、その実行結果も同一なので、言語処理系はcの出力を一回しか行わないかも知れません。 確実に二回cを出力させるには、確実に異なる引数を与える必要があります。
=world ((world different-world) c putc) (world c putc) merge-world

先のコードで、二つの処理((world different-world) c putc)と(world c putc)の返り値である「世界」はそれぞれ異なる値となるので、 関数merge-worldは異なる「世界」を同時に受けとることになります。 従って、同時には一つしか存在できない客観的な世界ではなく、 個々の入出力関数によって観測される複数の主観的な世界が、「世界型」で扱う値となります。

この三つにより、処理の回数・並列性・前後関係を表現できます。

言語処理系が最適な計算方法を探す手段として、データフロー解析は非常に重要です。 物理的な制約により、前の計算を終えるまでは次の計算が出来ない計算方法では速度に限界があります。 このため現在ではパソコンのCPUに至るまで並列計算の仕組みが組み込まれており、同時に計算しても構わない部分を検出する事が、 言語処理系にとって重要となります。 この並列計算検出の主役がデータフロー解析です。 参照透過性を持つ言語が効率的な計算方法を見つけることが出来るのは、データフロー解析を適切に行うことが出来るためです。 逆に言えば、データフロー解析を適切に行える言語であれば、 参照透過性を持つ言語と同じくらい効率の良い計算方法を、言語処理系は探すことが出来るはずです。
